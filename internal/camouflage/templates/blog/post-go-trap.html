记一次 Go map 遍历顺序引发的线上故障

2026-03-14分类：后端字数：约 2300 字阅读 4,217

上周三晚上十点，对账系统开始间歇性告警：同一笔订单，两次生成的对账单 diff 不为空。金额分毫不少，只是行的顺序变了。测试环境跑了半年一次没出过，生产上线第三天就炸。

排查过程

第一反应是并发改了数据。把两次请求的入参和中间状态 dump 出来对比，输入完全一致，输出内容一致、顺序不同——那就没有并发什么事了，纯纯的确定性代码给出了非确定性输出。

顺着 diff 生成的调用链往上找，三行之后就是它：

rows := make([]string, 0, len(summary))
for id, amt := range accountSummary {   // ← 元凶
    rows = append(rows, fmt.Sprintf("%s|%d", id, amt))
}
sort.Strings(rows)                      // 排序了，但排的是拼接后的字符串

等等，排序了还会乱？会。因为 fmt.Sprintf("%s|%d", ...) 里的 id 是账户号，而拼接前的 map 遍历顺序决定了……什么？不影响结果？不，真正的问题在下一层：

对账单尾部的"操作轨迹"字段是直接遍历操作日志 map 拼接的，没排序。之前没炸，只是因为测试数据少，恰好每次哈希桶布局一样。

为什么测试环境不复现

  • Go 的 map 遍历是随机的，但随机种子来自运行时；小 map 在基准测试式的固定输入下"看起来稳定"，给了所有人错觉；
  • 生产的 key 数量上去了（账户数 2w+），哈希冲突的桶链变长，随机性终于暴露；
  • CI 里没有对账单顺序断言，只有内容断言——这是流程要补的课。

修复与守则

ids := make([]string, 0, len(accountSummary))
for id := range accountSummary {
    ids = append(ids, id)
}
sort.Strings(ids)            // 先排 key
for _, id := range ids {
    rows = append(rows, fmt.Sprintf("%s|%d", id, accountSummary[id]))
}

组内定了两条守则：任何要落盘、要对外、要参与 diff/hash 的 map 输出，必须先取 key 排序；CR checklist 加了一条"这个循环的顺序重要吗？"。

最后统计了一下，这个坑我们组近三年踩了四次，分别在 Java（HashMap）、Python（dict 早期版本）、PHP 和这次的 Go。语言在变，坑没变：把"遍历顺序"当成"业务顺序"，是所有哈希容器的第一定律违例。
